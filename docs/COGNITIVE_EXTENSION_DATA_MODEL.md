# Learning OS Cognitive Extension Data Model

## Goal
The surface UI will change often. Learning history must not.

Learning OS therefore keeps the existing durable core (`nodes`, `sessions`, `records`, `relations`) and adds cognitive capabilities through an additive extension store rather than rewriting historical data.

## Two-layer persistence

### 1. Durable Core
Current canonical learning history remains in the core database:
- `nodes`: arbitrary-depth learning hierarchy
- `sessions`: deliberate learning periods
- `records`: append-first atomic learning events with full timestamps
- `relations`: typed connections between nodes or records

Core IDs are stable references. UI names such as Area / Thread / Topic are views, not schema constraints.

### 2. Cognitive Extension
Stored separately under `learningOS_cognitive_v4`.

Schema identifier:
`cognitive-extension/1.0`

The extension currently contains:
- `snapshots`: external-working-memory / mental-context snapshots
- `annotations`: additive interpretations attached to durable source records
- `hypotheses`: low-confidence derived patterns such as transition, incubation, or friction candidates
- `modelVersions`: the analysis rules/model that created derived hypotheses
- `dismissedHypotheses`: future support for learner feedback without deleting source evidence

The extension references stable core IDs (`nodeId`, `sessionId`, `recordId`) rather than copying the core data.

## Append-first rule
Historical source records should not be overwritten because a later theory or UI changes.

If the learner first writes:
`I do not understand physics`

and later specifies:
`The confusing part is choosing the axis for force decomposition`

the second statement should become a new record/annotation related to the first. The original expression remains historically true as a record of what was experienced at that time.

## Derived hypotheses are disposable; evidence is not
Patterns generated by an engine are not canonical truth.

Examples:
- repeated questions on a node
- `question -> distinction`
- delayed `revisit/question -> gotit` incubation candidate

These may be recalculated by future engines. Store their model version and confidence. Never alter source events merely because a derived pattern changes.

## No diagnostic identity fields
Do not create durable fields such as:
- `visual_learner=true`
- `poor_memory=true`
- `adhd_like=true`
- `low_ability=true`

Store contextual observations instead. A pattern is conditional, revisable, and may be contradicted by later evidence.

## Portable Bundle
Full backups use a wrapper rather than flattening all stores:

```json
{
  "bundleType": "learning-os-portable-bundle",
  "bundleVersion": 1,
  "exportedAt": "ISO timestamp",
  "core": { "...": "durable Learning OS core" },
  "extensions": {
    "cognitiveV4": { "...": "cognitive extension" }
  }
}
```

Future versions must preserve unknown extension namespaces whenever practical. This allows v5/v10 to add new engines without invalidating v4 data.

## Migration policy
1. Never silently delete old localStorage/database keys before a migration is verified.
2. Prefer additive migrations.
3. Keep source IDs stable.
4. Keep full timestamps.
5. Keep raw user expressions.
6. Derived models must be reconstructible from source records where practical.
7. Import should merge by stable IDs instead of replacing the user's entire history.
8. Export must include both core and installed extension stores.

## Current cognitive observations
The v4 underground can derive, cautiously:
- within-session `question/revisit -> distinction/gotit` transitions
- delayed same-node `question/revisit -> distinction/gotit` as incubation candidates
- repeated question nodes as friction candidates

These labels are hypotheses only. They deliberately do not infer cause, diagnosis, intelligence, learning style, or personality.

## Design principle
A new UI can be thrown away and rebuilt. A user's history of learning, thinking, confusion, distinctions, connections, and mental context should remain usable for years.
